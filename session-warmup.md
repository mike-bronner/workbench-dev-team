## Development workflow

For any code implementation, bug fix, refactor, or test-writing — manual or agent-driven — use the `/workbench-dev-team:develop` skill. It enforces shared development standards: read repo conventions first, plan before coding, atomic commits, every change gets a test, no committed secrets. Includes a decision protocol that requires presenting three options to the human (with reasoning and a recommendation) for any meaningful fork — the human decides, the agent executes. Applies universally, not just to dev-team automation.

## Git commits

For any git commit message — manual, scripted, or agent-driven — use the `/workbench-dev-team:git-commit` skill. It enforces Conventional Commits + Gitmoji format with full type/emoji references. This applies universally, not just to dev-team automation.

**Commit approval gate — non-negotiable.** A plugin `PreToolUse` hook enforces it at the harness level, and which lane you run in decides what you may do. **A sub-agent does not commit, does not merge, and does not push.** For any sub-agent it denies every git verb that writes a commit, integrates another history, or publishes one, plus `gh pr merge`; it prints no approval command and writes no approval record, because anything you can run yourself is not an approval. Hand the work back instead: leave the tree uncommitted, and report the diff and the proposed commit message to the session that dispatched you, which commits it. **In the foreground session, attempt the commit or the push yourself, and let the gate prompt.** Do not hand either one to the human to run. The gate denies every `git commit` and every `git push` until the human approves that exact command. It prompts only for the plain form: one line that is exactly `git [-C <path>] commit …`, `git [-C <path>] push …`, or `git [-C <path>] commit … && git [-C <path>] push …`, every word bare or quoted, with no `$`, backtick, or backslash inside double quotes, and no `cd`, pipe, redirect, comment, heredoc, variable, wrapper, or second line. Any other command that names git and a commit or push is refused with no approval path, so write the plain form from the start. Run `git add` as its own call, never chained. Write a multi-line message to a file in the session scratchpad and commit with `git commit -F <absolute path>`: Claude Code's default `git commit -m "$(cat <<'EOF' … EOF)"` is refused. Use `-C <path>` rather than `cd`. Shell aliases such as `gp` or `gcmsg` are not seen by the gate at all, so never use them for a commit or push. Present the diff and the proposed message for a commit, or the branch, remote, and commits it sends for a push. Then run the one command the denial prints: `bash "$HOME/.claude-workbench/bin/approve-commit.sh" <request-id> "<commit subject>"` for a commit, and the same command with no subject for a push. Run it exactly as printed, and only after the human has seen what it approves. Permission rules cover that command, so the harness raises a real prompt, and the human's answer is the approval. It covers that one command, in that session and directory, for 15 minutes, and the next run of the command spends it. A commit is also bound to HEAD and the staged diff, and a push to the repository's branches, tags, HEAD, and remote, branch, push, and url config, so any change before it runs voids the approval. A push that forces or deletes remote refs (`--force`, `-f`, `+refspec`, `--mirror`, `--delete`, `-d`, `:branch`, `--prune`) is refused with no approval path, and merge stays an explicit human request. **The only exemption is the autonomous Index pipeline**, recognized by `WORKBENCH_DEV_TEAM_PIPELINE=1`, which `bin/dispatch-agent.sh` exports onto the agent it spawns — there, board dispatch is the approval and Holmes review + human PR merge is the gate. Never set that variable yourself, never write an approval record by hand, and never edit the gate to get past it.

## Dev-team delegation

A three-agent dev team is installed as sub-agents: Inspector Lestrade (triage), Dr. Watson (development — supports ad-hoc Direct mode), Sherlock Holmes (code review). Development goes to Watson, triage to Lestrade, review to Holmes; anything ending in a changed file goes to one of them, never to a generic agent — `Explore`, `Plan`, and `general-purpose` are for read-only investigation. Invoke the `/workbench-dev-team:orchestrate` skill before dispatching: it carries the agent-choice rule, the five-slot brief template every handoff is written to (`Workdir:` / `Goal:` / `Context:` / `Constraints:` / `Done when:`, no shell commands or step lists, read-only research dispatches included), per-agent model/effort config, and roster tracking. `Goal:` runs to one or two sentences; `Context:` is prose and unbounded; `Constraints:` is bullets that each state their reason, and may read "none" where `Context:` may not. The brief binds the receiver too: an agent handed a brief short a slot refuses it and does no work, and one handed a complete brief it still can't finish sends its questions back rather than guessing. The rule reaches as far as the orchestrator boundary and no further: a specialist's own fan-out to internal workers is exempt, because the parent already holds every fact those workers need and their prompts are written against measured cost — a boundary rather than a list of agents, so a later specialist with a fan-out inherits it. The skill also routes GitHub action requests (review, comment, merge, triage) to the correct executor — The Index MCP for repos its GitHub App governs, `gh` CLI for the user's own actions and ungoverned repos — so invoke it for those requests too.
